# Эксплуатация серверов

Всё, что нужно знать после первого `make deploy`: секреты, несколько серверов, переезд
при блокировке и грабли, на которые уже наступали.

## Доступ

Вход только по SSH-ключу из `keys/` — пароль отключён (`ssh_disable_password: true`).
Роль откажется отключать пароль, пока на сервере нет ни одного ключа, так что одной
опечаткой отрезать себе доступ не выйдет.

**Потеряете `keys/vpn-infra` — попадёте на сервер только через аварийную консоль хостера**
(Console, VNC или KVM в панели). Стоит один раз проверить, что она открывается, и сделать
копию ключа в надёжном месте.

Первый заход на новый VPS: либо вставить `keys/vpn-infra.pub` в панели хостера при
создании, либо вписать root-пароль в `vault_ssh_password` (тогда на ПК нужен `sshpass`).

## Секреты

Пароли админок придумывает `make init` — случайные, по 32 символа. Запоминать их не
нужно: в админки заходят через SSH-проброс, а посмотреть пароль можно в любой момент.

```bash
make show-secrets   # показать пароли, ничего не меняя
make edit-secrets   # поправить прямо в зашифрованном файле
```

Пароль от самого vault лежит в `.vault-key` в корне проекта, один на все серверы, в git
не попадает. **Потеряете — vault не расшифровать**, сделайте копию в надёжном месте.
Ansible берёт ключ сам, вводить ничего не нужно.

Если удобнее править файл целиком обычным редактором:

```bash
make decrypt   # расшифровать все vault-файлы
make encrypt   # зашифровать обратно
```

`ping`, `check` и `deploy` ключ сами не создают, а останавливаются с подсказкой: иначе
потерянный ключ подменился бы новым, и ошибка выглядела бы как «Decryption failed».

`make hooks` включает проверку перед каждым коммитом: зашифрован ли vault, не попали ли
он, `.vault-key`, ssh-ключ и инвентарь под контроль версий, плюс gitleaks, yamllint,
ansible-lint и shellcheck. CI в проекте нет намеренно — это единственное место, где всё
проверяется, поэтому хуки стоит поставить сразу.

## Несколько серверов

Каждый живёт сам по себе: свой домен туннеля, свои ключи, свои клиентские конфиги.
Заблокируют один — остальные работают.

```bash
make new-host NAME=vpn-nl IP=203.0.113.10   # настройки нового сервера и запись в инвентаре
make hosts                                  # список
make deploy HOST=vpn-nl                     # развернуть только его
```

Ограничения `HOST=` и `TAGS=` работают для любой команды и комбинируются:
`make deploy HOST=vpn-nl TAGS=wireguard` тронет один сервис на одном сервере.
Прочее: `make upgrade` — деплой плюс обновление пакетов, `make backup` — снять
состояние в `artifacts/`, `make syntax` — проверка синтаксиса.

| Файл | Что задаёт | В git |
|---|---|---|
| `inventory/hosts.yaml` | список серверов и их адреса | нет |
| `host_vars/ИМЯ/vars.yaml` | набор сервисов, домен туннеля и резолвер — **свои у каждого** | нет |
| `host_vars/ИМЯ/vault.yaml` | SSH-пароль и пароли этого сервера | нет |
| `group_vars/all/vars.yaml` | общее для всех, в том числе набор сервисов по умолчанию | да |
| `group_vars/all/vault.yaml` | общие пароли админок (SSH-пароль здесь не хранить) | нет |

**Домен туннеля обязан быть свой у каждого сервера**: один поддомен на два сервера не
заработает, резолверы будут получать два разных ответа на один вопрос. Пароли тоже лучше
разные — тогда утечка одного сервера не открывает остальные.

SSH-пароли серверов не являются общими. Для каждого хоста задайте `vault_ssh_password`
в `host_vars/<имя>/vault.yaml` и зашифруйте файл командой `make encrypt`. Если старый
пароль лежит в `group_vars/all/vault.yaml`, удалите его оттуда после переноса. Каталог
`group_vars/<имя>` для этого не подходит: Ansible считает его переменными группы, а не
переменными конкретного хоста.

**Набор сервисов задаётся выключателями** — общий в `group_vars/all/vars.yaml`, для
отдельного сервера переопределяется в его `vars.yaml`: `wireguard_enabled`,
`xui_enabled`, `slipstream_enabled`, `dnstt_enabled`, `rustdesk_enabled`. Выключенный
сервис гасится, а порт файрвол не откроет. Открытые прежде правила ufw роль не
удаляет — убирать руками (`ufw delete allow <порт>/tcp`).

## Доступ к админкам

Обе админки — wg-easy и панель Xray — висят на loopback сервера. Снаружи их нет, из VPN
тоже. Единственный путь — SSH-проброс, и удобнее описать его один раз в `~/.ssh/config`
(на Windows это `C:\Users\<вы>\.ssh\config`):

```sshconfig
Host vpn
    HostName <IP сервера>
    User root
    IdentityFile ~/projects/vpn-infra/keys/vpn-infra
    LocalForward 51821 127.0.0.1:51821
    LocalForward 2053 127.0.0.1:2053
```

Дальше `ssh vpn`, не закрывая окно, — и в браузере:

- `http://127.0.0.1:51821` — wg-easy: создать клиента, скачать конфиг или снять QR-код;
- `http://127.0.0.1:2053/<путь>/` — панель Xray, путь печатает роль в конце прогона.

**Проброс разрешён не куда угодно.** В `sshd` стоит `PermitOpen` ровно на эти порты (список
собирается в `ssh_permit_open` по включённым сервисам), поэтому `-L` на любой другой порт
молча оборвётся — без единой записи в логах. Добавите сервис с админкой на loopback —
впишите его порт туда же, иначе потеряете вечер.

**Из самого VPN админка закрыта намеренно.** Раньше она открывалась по `http://10.8.0.1:51821`
любому, кому выдан конфиг, и это было удобно ровно до первого вопроса «а что он там может».
А может он много: счётчика попыток пароля у wg-easy нет вовсе, перебирать можно прямо через
API, а `GET /api/wireguard/backup` отдаёт ключи всех клиентов разом. То есть один выданный
конфиг плюс подобранный пароль — и у человека ключи остальных. Запрет ставится правилом в
`wireguard_post_up`, там же закрыт доступ из туннеля к docker-сетям, через которые была
достижима панель Xray.

## Если сервер заблокировали

Главная угроза — ковровая блокировка префикса хостера: ляжет и VPN, и DNS-туннель
(резолвер оператора ходит за ответом на тот же адрес). Защита — быстро поднять новый VPS
у другого хостера, в другой стране и AS.

Заготовить заранее, чтобы переезд занял минуты:

- **второй поддомен уже делегирован**: `t2` (NS → `ns2.<домен>`) и `ns2` (A → любой
  временный адрес). Делегирование расходится часами, ждать его в момент аварии — терять
  время; A-запись потом поправите;
- **свежий `make backup`** — состояние wg-easy и учётки туннеля в `artifacts/<сервер>/`.
  С ним новый сервер поднимается с теми же ключами, и конфиги, которые уже у людей на
  руках, продолжают работать. Снимать после каждого заведения клиента.

Порядок:

1. Купить VPS у другого хостера (другая страна и AS).
2. `make new-host NAME=vpn2 IP=<новый IP>`, вписать в `inventory/hosts.yaml`.
3. A-запись `ns2` → новый адрес.
4. В `host_vars/vpn2/vars.yaml` — домен `t2.<домен>`, резолвер, `wireguard_host`.
5. `make deploy HOST=vpn2 ARGS="-e wireguard_restore_src=artifacts/vpn1/wg-easy-state.tar.gz"`
   — только новый сервер, боевой не трогаем.
6. Перевести `wireguard_host` на новый адрес, старый сервер погасить.

Восстановление разворачивается только там, где своего состояния ещё нет, — рабочий сервер
случайным запуском не затрёшь. Ссылки туннеля выпускаются заново командой `slipnet-user`:
в них зашит домен, а он у каждого сервера свой.

**Куда переезжать** и как проверить свежий адрес до оплаты — в [HOSTING.md](HOSTING.md).
Коротко: другой хостер, другая страна, другая AS.

## Грабли, на которые уже наступали

- **Образы пинятся по версии** (`wg-easy:14`, `rustdesk-server:1.1.16`), `latest` не
  используется. wg-easy держим на v14: v15 переписан на веб-мастер и падает при заданном
  `PASSWORD_HASH`.
- **Деплой не перезагружает сервер сам** и не ставит обновления пакетов — этим занимается
  unattended-upgrades, с автоперезагрузкой в 04:30, если она нужна. Разово:
  `make deploy ARGS="-e common_auto_reboot=true"` и `make upgrade`.
- **Прогон нельзя прерывать** в ролях wireguard и rustdesk: контейнер пересоздаётся как
  «удалить старый → создать новый», обрыв посередине оставит сервис лежать.
- **Правила ufw только добавляются**, никогда не удаляются: лишнее убирать руками
  (`ufw delete allow <порт>/tcp`).
- **Портами ufw контейнеры Docker не закрыть**: Docker разворачивает трафик через DNAT в
  цепочке FORWARD, а ufw живёт в INPUT. По той же причине fail2ban не прикроет админку —
  баны пишутся в INPUT, а wg-easy к тому же не логирует неудачные входы.
- **Хэш пароля админки кэшируется** в `/root/.wg-easy.hash-<отпечаток>`: соль bcrypt
  случайная, без кэша каждый прогон пересоздавал бы контейнер. Смена пароля в vault меняет
  отпечаток, и хэш пересчитывается сам.
- **Своп создаётся ролью `swap`** (2 ГБ) и идёт первой: на машине с гигабайтом памяти он
  страхует от OOM во время apt-апгрейда.

## Безопасность

- **SSH — только ключ**, проброс портов закрыт, кроме локального `-L` на админки: список
  портов собирается в `ssh_permit_open` по включённым сервисам (сейчас wg-easy и панель
  Xray). Проброс unix-сокетов запрещён отдельно — через него доставали сокет докера.
  Раньше форвардинг был открыт целиком, и через него плюс пароль общей учётки вскрывалась
  админка.
- **Обе админки не смотрят ни наружу, ни в VPN** — только loopback сервера и SSH-проброс.
- **Пользователи туннеля до сервера не достают**: в конфиге прокси `deny` на loopback и
  частные сети. Проверить после правок в роли — зайти через туннель на `127.0.0.1:51821`,
  должно быть отказано.
- **Никаких учёток «только для туннеля»** — почему, написано в [TUNNEL.md](TUNNEL.md).
- **Секреты только в зашифрованном vault**, приватный ключ — в `keys/`, оба мимо git.
- После развёртывания проверить баны: `fail2ban-client status sshd`. Loopback fail2ban
  не банит, доступ изнутри сервера он не ограничивает.

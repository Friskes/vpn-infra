# DNS-туннель

Канал для случая, когда оператор включил белый список и обычный VPN не подключается
вообще (подробности — [OPERATORS.md](OPERATORS.md)). Разворачивает его роль `slipstream`;
здесь то, что Ansible за вас не сделает: домен, резолвер, настройки приложения.

**Как работает.** Телефон никогда не обращается к нашему серверу напрямую. Он задаёт
обычный вопрос резолверу своего оператора — разрешённому адресу, — а тот сам идёт за
ответом к нашему серверу. Данные едут внутри вопросов и ответов.

Наглядно, по шагам и с картинками, то же самое разобрано на отдельной странице:
**[как устроен DNS-туннель](https://friskes.github.io/vpn-infra/dns-tunnel-steps.html)**.

## Что нужно, кроме сервера

- домен с делегированным поддоменом (см. ниже);
- приложение [SlipNet](https://github.com/anonvector/SlipNet/releases) на телефоне
  (других клиентов нет, подробности — в [CLIENTS.md](CLIENTS.md#dns-туннель--только-slipnet));
- подобранный резолвер оператора — разница между ними до пяти раз по скорости.

## Домен

- **Короткое имя**: каждый символ суффикса съедает полезную нагрузку в каждом запросе.
- **Без слов `vpn`, `proxy`, `tunnel`** — имя видит оператор и каждый резолвер по пути.
- **Не в зоне `.ru`**: там нужны паспортные данные, а разделегирование по решению реестра
  убьёт все туннели разом, даже при живых серверах.

## Делегирование

Две записи, одна без другой бесполезна:

| Тип | Имя | Значение |
|---|---|---|
| A | `ns` | адрес сервера, **проксирование выключено** (серое облачко) |
| NS | `t` | `ns.<домен>` |

С включённым проксированием Cloudflare подменит адрес своим, и рекурсия придёт не к нам.
DNSSEC выключить.

Если у регистратора нет NS-записей (например, Timeweb) — перенести DNS в Cloudflare
(план Free) и прописать его серверы имён у регистратора. Отдавать регистратору весь
домен на свой сервер не стоит: падение сервера убьёт домен целиком.

Проверка, что делегирование доехало (от 15 минут до пары часов):

```bash
dig +short NS <домен>              # ожидаем серверы Cloudflare
dig +short A ns.<домен>            # ожидаем адрес сервера
dig +short NS t.<домен> @77.88.8.8
```

Cloudflare проверять **с сервера**: из России его серверы имён могут не отвечать.

## Подбор резолвера — главный рычаг

Смена резолвера меняет скорость в разы, тюнинг протокола не даёт ничего. **Просел канал —
первым делом перемерить резолверы.** Резолвер должен быть рекурсивным: «сайт в белом
списке» не значит «его сервер имён даст рекурсию».

### Коротко: как найти свой резолвер за 10 минут

Резолвер — это сервер имён, которому ваш телефон задаёт вопросы «какой адрес у
такого-то сайта». Нам нужен такой, который оператор пропускает (обычно это его
собственные) и который умеет **рекурсию** — то есть сам пойдёт спрашивать нашу
зону, а не ответит «не знаю».

1. **Выключить Wi-Fi и VPN**, остаться на мобильном интернете нужного оператора.
2. Открыть SlipNet → профиль → **Scan for Working Resolvers**, страна — своя.
   Приложение переберёт свою базу и оставит те, что отвечают и доносят рекурсию.
   <!-- media: resolver-scan.png — экран Scan for Working Resolvers с результатами -->
   <!-- media: slipnet-profile.png — импортированный профиль и поле DNS Resolver -->
3. Взять из списка 3–5 кандидатов и **померить каждый** (порядок ниже): бейджи
   приложения говорят «работает», но не говорят «быстро», а разница до пяти раз.
4. Лучший вписать в `slipstream_default_resolver` в `host_vars/<сервер>/vars.yaml` —
   тогда он попадёт во все выдаваемые ссылки.

**Резолвер подбирается под оператора и регион клиента, а не под сервер.** У друга
на другом операторе будет свой; выдать ему ссылку с другим резолвером —
`slipnet-user link <имя> <IP резолвера>`.

**Если сканер ничего не нашёл.** Резолверы оператора видны на телефоне: на Android 16
и новее — `adb shell dumpsys connectivity | grep -i dns`, на старых — в настройках
сети. Соседние адреса той же подсети обычно тоже отвечают: возьмите найденный
адрес, переберите его `/24` и посмотрите, чьи запросы доехали до сервера — это
делает `tools/measure/resolver-race.sh` из [MEASURE.md](MEASURE.md). Всё, что
доехало, — кандидаты на замер скорости.

> Публичные резолверы (`8.8.8.8`, `1.1.1.1`) под ограничениями обычно закрыты, а
> без ограничений всё равно медленнее операторских: до них дальше идти. Начинать
> стоит с адресов своего оператора.

### Порядок подбора

Кандидатов ищет само приложение: кнопка **Scan for Working Resolvers** в профиле. У него
база на 60 тысяч адресов, сканирование по стране или по своему списку, проверка на подмену
DNS, на урезанный размер ответа и на то, доходит ли рекурсия до нашей зоны.

Чего приложение не показывает — **сколько килобайт в секунду резолвер реально вытягивает**.
А разница огромна: адрес, прошедший все проверки приложения, давал 25 КБ/с там, где другой
давал 215. Это меряет `tools/measure/tunnel-speed.py` — качает файл через локальный SOCKS
приложения, то есть ровно тем путём, которым ходит весь трафик телефона.

1. В приложении Scan → дождаться списка прошедших.
2. Кандидата из списка вписать в поле DNS Resolver и **переподключить VPN** — иначе
   останется старая сессия и замер покажет прежний резолвер.
3. В Termux `python tunnel-speed.py` — полминуты, честные КБ/с.
4. Повторить для следующего кандидата, оставить лучший.

Подготовка Termux (один раз): поставить [Termux](https://f-droid.org/packages/com.termux/)
из F-Droid, в нём `pkg install python` и `termux-setup-storage`. Скрипт занести с ПК по
кабелю: `adb push tools/measure/tunnel-speed.py /sdcard/Download/`, затем в Termux
`cp ~/storage/downloads/tunnel-speed.py .`

```bash
python tunnel-speed.py                          # три прогона по 8 с, берём лучший
python tunnel-speed.py --runs 1                 # быстрая проверка, ~1 МБ трафика
python tunnel-speed.py --expect-ip 203.0.113.10  # заодно сверить, что вышли через сервер
```

Каждый прогон съедает около мегабайта мобильного трафика. `--expect-ip` стоит указывать
всегда: если наружу мы выходим не с адреса сервера, туннель не работает вовсе, а цифры
показывают скорость обычного мобильного интернета.

### Что уже измерено

Цифры по конкретным операторам и резолверам — в [MEASUREMENTS.md](MEASUREMENTS.md):
какой резолвер сколько даёт, где канал рвётся и какие догадки уже проверены. Там же
то, что экономит время при следующем подборе.

Коротко: на МТС рабочий резолвер даёт 154–215 КБ/с, а соседний из того же списка — 25.
На Мегафоне Slipstream не тянет вовсе, и там нужен второй туннель — о нём ниже.

## Когда Slipstream не тянет: второй туннель

Slipstream общается с резолвером только по UDP. Если оператор душит поток DNS-ответов,
сделать с этим нечего: размер ответа и частота запросов у Slipstream не настраиваются.
Так ведёт себя Мегафон — замеры ниже.

На этот случай на сервере поднят **dnstt** (роль `dnstt`). Он умеет ходить к резолверу по
**TCP, DoT и DoH**, а их фильтр не трогает: у Мегафона под белым списком открыты
`77.88.8.8:853` (DoT, 124 мс) и `10.93.233.228:53` по TCP (82 мс). Оба туннеля живут
одновременно и не мешают друг другу: у них разные зоны и разные адреса — `53/udp` на IPv4
занимает Slipstream, dnstt слушает IPv6.

Делегирование для него — ещё две записи, обе с выключенным проксированием:

| Тип | Имя | Значение |
|---|---|---|
| AAAA | `ns6` | IPv6-адрес сервера |
| NS | `d` | `ns6.<домен>` |

**A-запись для `ns6` не заводить.** Рекурсор пошёл бы по IPv4 на порт 53, где слушает
Slipstream, и получил бы NXDOMAIN. Обратная сторона: зона доступна только рекурсорам с
IPv6 — у публичных резолверов он есть, но проверить после делегирования обязательно:
`dig +short TXT test.d.<домен> @77.88.8.8` должен вернуть ответ, а не таймаут.

Профиль для приложения печатает `dnstt-profile` на сервере: домен и публичный ключ. В
SlipNet заводится профиль типа **DNSTT**, где кроме них указываются транспорт (DoT) и
резолвер. Логин и пароль SOCKS5 — те же, что у Slipstream, туннель заканчивается на том же
прокси.

На Мегафоне dnstt дал 2,8 КБ/с против 0,3 у Slipstream — цифры и подробности в
[MEASUREMENTS.md](MEASUREMENTS.md). Тумблер **Authoritative Mode в профиле dnstt включать
нельзя**: с ним запросы вообще перестают доходить до сервера.

Локальный SOCKS у dnstt-профиля просит логин и живёт на своём порту (у нас 10882, у
Slipstream 10880), поэтому замер запускается так:

```bash
python tunnel-speed.py --socks-port 10882 --socks-user <имя> --socks-pass <пароль>
```

Рукопожатие через еле живой канал занимает до 15 секунд — это норма, а не поломка.

## Настройки SlipNet

Каждое значение — результат замера:

| Параметр | Значение | Почему |
|---|---|---|
| Congestion Control | **BBR** | 241 против 111 КБ/с у DCubic, разброс между прогонами исчезает |
| VPN MTU | **1100** | 227–235 КБ/с против 114–172 у дефолтных 1280 |
| DNS workers | **Per-query** | иначе теряется половина канала |
| Keep Alive | **400 мс** | 200 и 800 проверены, хуже |
| Disable QUIC | **вкл** | иначе приложения ждут таймаут на QUIC, который через SOCKS не проходит |
| GSO, Authoritative Mode | выкл | первый ненадёжен через VpnService, второй ходит к серверу напрямую |

MTU **зависит от длины домена**: при 1100 пакет укладывается в целое число DNS-ответов.
Сменили домен — подбор повторить. Public Key задавать не нужно, у Slipstream своё
шифрование. Compression, Max Channels, Buffer Size и таймауты приложение для этого типа
туннеля не использует.

## Выдача доступа

Туннель отзывается всем, кто знает домен, поэтому за ним стоит SOCKS5 с паролем (3proxy):

```bash
slipnet-user add petya            # заведёт и напечатает ссылку slipnet://...
slipnet-user link petya 213.87.74.21   # та же ссылка, но с другим резолвером
slipnet-user list                 # кто заведён
slipnet-user del petya            # отозвать доступ (обрывает и живые сессии)
```

Ссылка вставляется в SlipNet через «Import from URI» и заполняет профиль целиком.
Пользователи туннеля ходят только в интернет: доступ на сам сервер закрыт правилом `deny`
в конфиге прокси.

**Учёток «только для туннеля» на сервере быть не должно.** Оболочка `nologin` не мешает
пробросу портов — он открывается раньше оболочки. Старая учётка `tunnel` от схемы с SSH
внутри туннеля однажды уже стала дырой: пароль разошёлся по мессенджерам, а через проброс
открывалась админка.

## Когда «туннель не грузит»

1. Прокси пишет строку на каждое соединение в `/var/log/3proxy/3proxy.log.<дата>`: учётка,
   код ошибки, адрес назначения, байты, длительность. Прошедшее соединение — код `00000`
   с именем учётки. Ненулевой код и пустая учётка означают, что до авторизации дело не
   дошло; таких строк хватает и в норме (приложения открывают соединения про запас).
   **Тревожно, когда строк с `00000` нет вовсе** — тогда не пускает прокси, а не канал.
2. Сам туннель — `journalctl -u slipstream`.
3. Если оба живы — `python tunnel-speed.py` с телефона и подбор резолвера заново.

## Тупики: проверено, не повторять

- **Синтетический стенд обманывает**: на `tc netem` увеличение окна давало +35%, на живом
  канале то же изменение — минус 35%. Узкое место не задержка, а резолвер оператора.
- **Тюнинг окна и запросов в полёте** — заводские значения оптимальны.
- **DoH** (`1.1.1.1/dns-query`) — адрес под ограничениями закрыт. Отсюда общее правило:
  **клиентский лог врёт, проверять появление сессии на сервере**.
- **iodine** — по расчётам быстрее, на деле медленнее: шлёт запросы по очереди.
- **dnstt** — на живом канале в десять раз медленнее Slipstream (22–45 против 241 КБ/с):
  QUIC не тормозит весь поток из-за одного потерянного пакета.
- **EDNS больше 1232 байт** — сервер отвечает FORMERR. **Сжатие в туннеле** — бесполезно,
  трафик уже зашифрован.

Незакрытый резерв: в VPN-режиме приложение теряет около 60% против чистого клиента.
Per-App Proxy (пустить в туннель только нужные приложения) не проверялся.

## Если понадобится собрать сервер вручную

```bash
git clone --recursive https://github.com/Mygod/slipstream-rust.git
cargo build --release -p slipstream-server
```

Обязательно с подмодулями, иначе сборка падает на picoquic. На VPS не собирать — там одно
ядро и гигабайт памяти. Слушать `:53` целиком нельзя (порт занят systemd-resolved) —
биндиться на внешний адрес, как это делает роль. Установщик `slipstream-socks-deploy`
не использовать: он ломает `/etc/resolv.conf`.
